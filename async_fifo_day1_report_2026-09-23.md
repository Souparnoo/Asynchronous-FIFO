## 1. Project Overview

The objective of this project is to design and verify an **asynchronous
FIFO (First-In First-Out buffer)** in Verilog.

An asynchronous FIFO is used when data has to move safely between two
independent clock domains. Unlike a synchronous FIFO, the write side and
read side do not share the same clock.

For this project, the initial specification is:

  Parameter                                         Value
  ------------------------------------------------- ----------------------------------------------
  FIFO type                                         Asynchronous FIFO
  Data width                                        8 bits
  Memory depth                                      64 entries
  Usable FIFO capacity in the chosen architecture   63 entries
  Write clock                                       80 MHz
  Read clock                                        50 MHz
  Write clock period                                12.5 ns
  Read clock period                                 20 ns
  Write reset                                       Active-low, write-domain reset
  Read reset                                        Active-low, read-domain reset
  Status flags                                      `full`, `empty`
  CDC approach in Day 1                             Two-stage synchronization of binary pointers
  Pointer representation in Day 1                   Binary
  Gray code                                         Not used in the current Day 1 implementation
  Extra wrap bit                                    Not used in the current Day 1 implementation

The purpose of Day 1 was not to build the final production-grade CDC
architecture immediately. The goal was to first understand the FIFO
architecture, implement a working simulation model, understand the
pointer and flag logic, and build a self-checking testbench.

Further architectural improvements and hardware-safe CDC work can be
added later.

------------------------------------------------------------------------

# 2. What Is a FIFO?

FIFO stands for **First-In First-Out**.

The basic rule is:

> The first piece of data written into the FIFO must be the first piece
> of data read from the FIFO.

For example:

``` text
Write:  A → B → C → D

Read:   A → B → C → D
```

A FIFO therefore needs two independent positions:

-   A **write pointer** indicating where the next write happens.
-   A **read pointer** indicating where the next read happens.

Conceptually:

``` text
                 FIFO MEMORY

       Write pointer                 Read pointer
             │                            │
             ▼                            ▼

        ┌───────┬───────┬───────┬───────┐
        │       │       │       │       │
        │ DATA  │ DATA  │ DATA  │ DATA  │
        │       │       │       │       │
        └───────┴───────┴───────┴───────┘
```

The write pointer advances when a valid write occurs.

The read pointer advances when a valid read occurs.

------------------------------------------------------------------------

# 3. Why an Asynchronous FIFO?

A normal synchronous FIFO assumes:

``` text
wr_clk = rd_clk
```

or at least that all logic operates in one clock domain.

That is not true for an asynchronous FIFO.

In this project:

``` text
Write clock = 80 MHz
Read clock  = 50 MHz
```

The clocks are independent.

Their edges do not have a fixed phase relationship.

Therefore:

``` text
wr_clk  ──┐   ┌───┐   ┌───┐   ┌───┐
          └───┘   └───┘   └───┘

rd_clk  ─────┐   ┌────┐   ┌────┐
             └───┘    └────┘
```

The read side cannot simply assume that a pointer generated by the write
side is already stable.

This makes **clock-domain crossing (CDC)** the central concept of an
asynchronous FIFO.

------------------------------------------------------------------------

# 4. Project Architecture Chosen on Day 1

The architecture developed during Day 1 is a relatively simple
simulation-oriented asynchronous FIFO.

The main blocks are:

``` text
                    ASYNCHRONOUS FIFO

                 ┌─────────────────────┐
                 │     FIFO MEMORY     │
                 │      64 × 8         │
                 └─────────────────────┘
                     ▲             ▲
                     │             │
                  WRITE          READ
                     │             │
                     │             │
              ┌──────┴───┐   ┌─────┴──────┐
              │  Write   │   │    Read    │
              │ Pointer  │   │   Pointer  │
              └──────┬───┘   └─────┬──────┘
                     │             │
                     │             │
               2-FF CDC       2-FF CDC
                     │             │
                     ▼             ▼
                Read pointer   Write pointer
                in write clk   in read clk
                     │             │
                     ▼             ▼
                  FULL logic    EMPTY logic
```

The architecture has four important parts:

1.  FIFO memory
2.  Write pointer
3.  Read pointer
4.  Cross-domain synchronized pointer copies

------------------------------------------------------------------------

# 5. FIFO Memory

The memory is:

``` verilog
reg [7:0] mem [0:63];
```

This means:

``` text
64 locations
8 bits per location
```

Therefore:

``` text
Total storage = 64 × 8
              = 512 bits
```

The write side accesses:

``` verilog
mem[wp] <= din;
```

The read side accesses:

``` verilog
dout <= mem[rp];
```

The memory is therefore accessed from two different clock domains.

------------------------------------------------------------------------

# 6. Write Side

The write side operates using `wr_clk`.

The basic logic is:

``` verilog
always @(posedge wr_clk or negedge wr_reset_n) begin
    if (!wr_reset_n)
        wp <= 0;

    else if (wr_en && !full) begin
        mem[wp] <= din;

        if (wp == 63)
            wp <= 0;
        else
            wp <= wp + 1;
    end
end
```

The important condition is:

``` verilog
wr_en && !full
```

A write is accepted only when:

``` text
write enable = 1
AND
FIFO is not full
```

If `full = 1`, the write pointer must not move and the incoming data
must not overwrite existing FIFO contents.

------------------------------------------------------------------------

# 7. Read Side

The read side operates using `rd_clk`.

The logic is:

``` verilog
always @(posedge rd_clk or negedge rd_reset_n) begin
    if (!rd_reset_n)
        rp <= 0;

    else if (rd_en && !empty) begin
        dout <= mem[rp];

        if (rp == 63)
            rp <= 0;
        else
            rp <= rp + 1;
    end
end
```

A read is accepted only when:

``` text
read enable = 1
AND
FIFO is not empty
```

If `empty = 1`, the read pointer must not advance.

------------------------------------------------------------------------

# 8. Why We Initially Did Not Use Gray Code

During the design discussion, the standard asynchronous FIFO solution
using **Gray-coded pointers** was considered.

Normally, an asynchronous FIFO uses:

``` text
Binary pointer
      ↓
Gray-code conversion
      ↓
Clock-domain synchronizer
      ↓
Other clock domain
```

Gray code is preferred because only one bit changes between adjacent
Gray-code values.

For example, binary can transition:

``` text
011111
100000
```

where many bits change at once.

That creates a problem when a multi-bit binary counter crosses an
asynchronous clock boundary.

However, for Day 1, the decision was deliberately made to first build a
simpler **simulation-oriented FIFO** using binary pointers.

The reasoning was:

1.  First understand the FIFO mechanics.
2.  Make the pointer movement and memory behavior work.
3.  Verify `full` and `empty`.
4.  Verify wraparound.
5.  Build a self-checking testbench.
6.  Later improve the CDC implementation using Gray code.

This separates **functional understanding** from **CDC-hardening**.

The current implementation should therefore not be described as a final
silicon-safe asynchronous FIFO CDC implementation. It is the first
functional architecture.

------------------------------------------------------------------------

# 9. Why We Did Not Use an Extra Wrap Bit

A standard asynchronous FIFO commonly uses an extra pointer bit.

For a 64-entry FIFO:

``` text
Address bits = log2(64)
             = 6
```

A conventional implementation can therefore use:

``` text
7-bit pointer
```

where:

``` text
[5:0] = memory address
[6]   = wrap information
```

For Day 1, this was intentionally avoided.

Instead, the pointer is:

``` verilog
reg [5:0] wp;
reg [5:0] rp;
```

and explicitly wraps:

``` verilog
if (wp == 63)
    wp <= 0;
else
    wp <= wp + 1;
```

Similarly for `rp`.

------------------------------------------------------------------------

# 10. Why the FIFO Capacity Is 63 Instead of 64

This is an important part of the chosen architecture.

With only the six-bit read and write pointers, the same pointer value
can mean two different things:

``` text
wp == rp
```

could mean:

``` text
FIFO EMPTY
```

but after a complete circular wrap it could also represent:

``` text
FIFO FULL
```

To avoid this ambiguity, one location is intentionally left unused.

Therefore:

``` text
Memory capacity = 64
Usable FIFO capacity = 63
```

This is a common simple circular-buffer technique.

------------------------------------------------------------------------

# 11. Full Detection

The chosen full logic is:

``` verilog
full = (wp == 63) ? (rp_sync == 0) :
                     (rp_sync == wp + 1);
```

This can be understood as:

``` text
FULL when the NEXT write position
would collide with the read position.
```

For normal positions:

``` text
next_wp = wp + 1
```

so:

``` text
full = (next_wp == rp_sync)
```

For the special case:

``` text
wp = 63
```

the next pointer wraps:

``` text
63 → 0
```

so:

``` text
full = (rp_sync == 0)
```

This is why the conditional expression was used.

------------------------------------------------------------------------

# 12. Empty Detection

The empty condition is much simpler:

``` verilog
empty = (rp == wp_sync);
```

The read side compares:

``` text
current read pointer
```

with:

``` text
synchronized write pointer
```

If they are equal:

``` text
There is no unread data visible to the read domain.
```

------------------------------------------------------------------------

# 13. Why Pointer Synchronization Is Required

The write pointer belongs to:

``` text
wr_clk domain
```

The read pointer belongs to:

``` text
rd_clk domain
```

Therefore the write side cannot directly use the raw read pointer, and
vice versa.

The architecture uses two DFF stages.

### Read pointer entering write domain

``` text
rd_clk domain

rp
 │
 ▼
┌─────────┐
│ DFF #1  │
└────┬────┘
     │
     ▼
┌─────────┐
│ DFF #2  │
└────┬────┘
     │
     ▼
rp_sync
```

Both DFFs use `wr_clk`.

### Write pointer entering read domain

``` text
wr_clk domain

wp
 │
 ▼
┌─────────┐
│ DFF #1  │
└────┬────┘
     │
     ▼
┌─────────┐
│ DFF #2  │
└────┬────┘
     │
     ▼
wp_sync
```

Both DFFs use `rd_clk`.

The two-stage structure is intended to give metastability more time to
resolve before the synchronized signal is used by normal logic.

Again, because Day 1 uses **binary pointer synchronization**, this is a
functional learning implementation rather than the final recommended CDC
architecture.

------------------------------------------------------------------------

# 14. The DFF Module

A reusable six-bit DFF was created:

``` verilog
module dff(
    input clk,
    input reset_n,
    input [5:0] d,
    output reg [5:0] q
);

    always @(posedge clk or negedge reset_n) begin
        if (!reset_n)
            q <= 0;
        else
            q <= d;
    end

endmodule
```

This module is instantiated four times:

``` text
1. rp → rp_sync1
2. rp_sync1 → rp_sync
3. wp → wp_sync1
4. wp_sync1 → wp_sync
```

------------------------------------------------------------------------

# 15. Testbench Problem: Infinite Read Loop

The first large testbench had a serious verification problem.

The testbench used logic similar to:

``` verilog
while (ref_count > 0)
    do_read;
```

However, `ref_count` belonged to the reference model while the DUT's
`empty` flag could temporarily indicate empty because of the
asynchronous pointer synchronization delay.

This created a situation such as:

``` text
ref_count = 1
empty = 1
```

Then:

``` text
do_read()
    ↓
FIFO EMPTY
    ↓
ref_count does not change
    ↓
while(ref_count > 0)
    ↓
do_read()
    ↓
FIFO EMPTY
    ↓
...
```

The simulator consequently printed:

``` text
READ BLOCKED | FIFO EMPTY
READ BLOCKED | FIFO EMPTY
READ BLOCKED | FIFO EMPTY
...
```

indefinitely.

This was a major lesson in verification:

> A testbench should never contain an unbounded wait condition that
> depends on a signal which might never change because the DUT has
> failed.

The corrected testbench uses bounded loops and timeout protection.

# 16. Final Testbench Architecture

The final testbench is self-checking.

It contains:

``` text
                 TESTBENCH
                     │
        ┌────────────┴────────────┐
        │                         │
    Write driver              Read driver
        │                         │
        ▼                         ▼
      DUT                       DUT
        │                         │
        └────────────┬────────────┘
                     │
                Scoreboard
                     │
                     ▼
              Expected data
                     │
                     ▼
                Comparison
                     │
                     ▼
                PASS / FAIL
```

The testbench does not simply display waveforms.

It actively checks whether the data coming out of the FIFO matches the
data that should have come out.

------------------------------------------------------------------------

# 17. Scoreboard Concept

The testbench maintains a reference FIFO:

``` verilog
reg [7:0] expected_fifo [0:62];
```

When a write is actually accepted:

``` text
wr_en = 1
AND
full = 0
```

the testbench records the input data.

When a read is actually accepted:

``` text
rd_en = 1
AND
empty = 0
```

the testbench compares:

``` text
DUT dout
```

against:

``` text
expected FIFO front
```

Therefore the testbench checks the most important FIFO property:

``` text
DATA OUT == DATA THAT WAS WRITTEN FIRST
```

------------------------------------------------------------------------

# 18. Why the Testbench Uses `#1` After Read

The DUT performs:

``` verilog
dout <= mem[rp];
```

using a non-blocking assignment.

Therefore, when the read clock edge occurs, the new value of `dout` is
scheduled for the NBA update region.

The testbench uses a small delay:

``` verilog
#1;
```

before comparing the output.

This gives the DUT's non-blocking assignment time to update `dout`.

Without this, the testbench could compare the old `dout` value and
report a false failure.

------------------------------------------------------------------------

# 20. Test Cases

The verification plan developed for Day 1 contains eight major tests.

## Test 1 --- Basic Write / Read

Data such as:

``` text
11
22
33
44
```

is written and then read.

Expected:

``` text
11
22
33
44
```

This verifies basic FIFO ordering.

------------------------------------------------------------------------

## Test 2 --- Fill FIFO

The FIFO is filled with:

``` text
63 entries
```

because one location is intentionally reserved.

The test then checks:

``` verilog
full == 1
```

This verifies the full-generation logic.

------------------------------------------------------------------------

## Test 3 --- Write While Full

Once `full = 1`, another write is attempted.

The expected behavior is:

``` text
FIFO contents remain unchanged.
Write pointer does not advance.
```

This verifies protection against overflow.

------------------------------------------------------------------------

## Test 4 --- Drain FIFO

The FIFO is read until:

``` verilog
empty == 1
```

The testbench verifies that all data comes out in FIFO order.

This tests:

``` text
FIFO ordering
pointer movement
read logic
empty generation
```

------------------------------------------------------------------------

## Test 5 --- Read While Empty

After the FIFO becomes empty, another read is attempted.

Expected:

``` text
No pointer movement.
No valid new data is consumed.
```

This verifies protection against underflow.

------------------------------------------------------------------------

## Test 6 --- Pointer Wraparound

The test performs more than 64 transactions.

The objective is to force:

``` text
63 → 0
```

for both write and read pointers.

This verifies that the circular addressing logic works correctly.

------------------------------------------------------------------------

## Test 7 --- Burst Traffic

A burst of data is written and then drained.

This tests behavior when many entries are present simultaneously rather
than only one-at-a-time traffic.

------------------------------------------------------------------------

## Test 8 --- Random Asynchronous Traffic

The final test runs independent random write and read activity.

The write and read sides operate concurrently.

The test therefore exercises:

``` text
Different clock frequencies
Random enable patterns
Full conditions
Empty conditions
Pointer synchronization
Pointer wraparound
FIFO ordering
```

This is the most representative functional test of Day 1.

# 24. Timeout Protection

One of the major changes made to the testbench was adding bounded
waiting.

For example:

``` verilog
while (empty && timeout < 20)
```

instead of waiting forever.

Likewise, FIFO draining is bounded:

``` verilog
while (!empty && timeout < 100)
```

This means a broken DUT cannot make the simulator run indefinitely.

Instead, the testbench reports something like:

``` text
ERROR: TIMEOUT WAITING FOR FIFO DATA
```

This is an important verification practice.

# 25. What I Learned From This Project

Day 1 was not only about getting an asynchronous FIFO to compile.

Several practical Verilog and digital-design concepts were reinforced.

### 25.1 Clock-domain crossing is different from normal logic

A signal generated in one clock domain cannot simply be assumed to be
safe in another clock domain.

The clock domains must be treated independently.

------------------------------------------------------------------------

### 25.2 FIFO flags depend on pointer information

`empty` and `full` are fundamentally pointer-comparison problems.

The memory itself is relatively simple.

The difficult part is determining:

``` text
Where is the write side?
Where is the read side?
Is there unread data?
Is there available space?
```

------------------------------------------------------------------------

### 25.3 A circular pointer needs special handling

With a finite memory:

``` text
63 → 0
```

must be explicitly handled.

Otherwise the pointer would overflow.

------------------------------------------------------------------------

### 25.4 Full and empty are not symmetric in a simple circular buffer

Empty:

``` text
rp == synchronized wp
```

Full requires checking where the **next write** would land.

That led to:

``` verilog
full = (wp == 63) ? (rp_sync == 0)
                  : (rp_sync == wp + 1);
```

------------------------------------------------------------------------

### 25.5 Simulation correctness and hardware CDC correctness are different

This was one of the most important lessons.

The current Day 1 implementation can be functionally simulated with
asynchronous clocks.

However, simulation does not reproduce real analog metastability
behavior.

Therefore:

``` text
Functional simulation passing
≠
CDC implementation automatically being silicon-safe
```

The next architectural improvement is to use Gray-coded pointers for the
CDC path.

------------------------------------------------------------------------

### 25.6 Testbench design is itself a design problem

The infinite-loop issue showed that a testbench can be wrong even when
the DUT is the thing being tested.

A good testbench must have:

``` text
Stimulus
Reference model
Checking
Timeouts
Error reporting
Final PASS/FAIL
```

rather than simply applying inputs and watching waveforms.

------------------------------------------------------------------------

A conventional implementation will use:

``` text
ADDR_WIDTH + 1
```

pointer bits.

For a 64-entry FIFO:

``` text
6 address bits
+
1 wrap bit
=
7-bit pointer
```

This allows the FIFO to distinguish full and empty without intentionally
wasting one memory location.

# 30. Vivado Simulation Issue Found After Day 1

After the testbench was working in **Icarus Verilog**, the same testbench
was run in **Vivado simulation**.

A simulator-specific issue was observed.

The simulation was progressing only up to approximately:

``` text
100 ns
```

and then became stuck during:

``` text
TEST 2 --- Fill FIFO
```

The important observation is:

``` text
Icarus Verilog → testbench runs successfully
Vivado        → simulation gets stuck around Test 2
```

Therefore, this is currently being treated as a **testbench/simulation
scheduling issue that needs further debugging**, rather than immediately
assuming that the FIFO RTL itself is incorrect.

## 30.1 Why This Is Being Investigated

Test 2 attempts to fill the FIFO with 63 entries and then verify:

``` verilog
full == 1
```

The FIFO uses:

``` text
80 MHz write clock
50 MHz read clock
```

so the two clock domains continue operating independently.

The testbench also interacts with the DUT at clock edges. Different
simulators can expose differences in event scheduling and race conditions,
especially when the testbench and DUT both react to the same clock edge.

The current suspicion is therefore around the **testbench synchronization,
event scheduling, or a wait condition**, rather than concluding that the
FIFO design is broken.

## 30.2 Debugging Approach

The next debugging step is to make Test 2 completely observable.

Debug messages will be added around each write so that the simulation can
show:

``` text
write number
write pointer
synchronized read pointer
full flag
```

For example:

``` verilog
$display("[%0t] Write %0d: wp=%0d full=%b",
         $time, i, dut.wp, full);
```

The beginning and end of Test 2 will also be explicitly printed:

``` verilog
$display("[%0t] TEST 2 START", $time);
```

and:

``` verilog
$display("[%0t] TEST 2 WRITES COMPLETE", $time);
```

This will identify the exact transaction at which Vivado stops progressing.

## 30.3 Important Observation About Test 2

The test does not need to wait indefinitely for `full` while performing the
63 writes.

The FIFO has a known usable capacity of:

``` text
63 entries
```

Therefore, Test 2 can perform exactly 63 deterministic write transactions,
then allow the `full` logic to settle and check the resulting flag.

This avoids making the main fill loop dependent on a potentially problematic
wait condition.

The intended structure is:

``` text
Start Test 2
     ↓
Perform 63 write-clock transactions
     ↓
Stop writing
     ↓
Allow full logic to settle
     ↓
Check full == 1
     ↓
End Test 2
```

This is also useful for debugging because the exact write at which the
simulation stops becomes visible.

## 30.4 Current Status of This Issue

At this stage:

``` text
RTL compilation              → working
Icarus Verilog simulation    → working
Vivado simulation            → gets stuck around 100 ns
Problem location             → Test 2, FIFO fill
Root cause                   → still being investigated
```

The issue is therefore recorded as an **open Day 1 verification/debugging
item**.

No change is being made to the FIFO architecture solely based on this
simulator difference until the exact cause is identified.
